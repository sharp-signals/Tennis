## Decisão

O pipeline mantém o acervo automático Wikidata/Wikimedia Commons e passa a
aceitar um pequeno registo manual, auditável e fail-closed para fotografias
cuja fonte não está ligada por P18. A ordem é:

1. override manual com identidade, licença, crédito e asset local válidos;
2. registo existente proveniente de Wikidata/Wikimedia Commons;
3. avatar de iniciais no relatório.

Um override inválido nunca quebra a geração: é ignorado e a resolução continua
para Commons ou iniciais. Não há hotlinking; o HTML referencia apenas o asset
versionado em `docs/assets/players/`.

## Contrato do override

`data/player_image_overrides.json` usa chaves estáveis `tour:player_id`. Cada
entrada exige `tour`, `player_id`, `name`, `source_url`, `author`, `license`,
`license_url`, `path` e `modifications`. A validação confirma:

- circuito ATP/WTA, coerência entre chave e ID e nome canónico não vazio;
- URLs web factuais para fonte original e licença;
- licença aberta admitida: CC0, CC BY, CC BY-SA ou domínio público;
- rejeição explícita de licenças NC, ND e All Rights Reserved;
- existência do ficheiro e confinamento do caminho a
  `docs/assets/players/`, impedindo hotlinks e path traversal.

Os campos `author`, `license`, `license_url`, `source_url` e `modifications`
alimentam o bloco já existente «Créditos das fotografias». Não foi criado um
segundo sistema visual de créditos.

## Fila de revisão

A sincronização preserva casos pendentes, atualiza metadados observacionais e
remove um caso apenas quando a identidade passa a resolver para um asset
licenciado válido. Reason codes manualmente curados não dependem do estado
transitório da fila: são lidos do ficheiro declarativo
`data/player_image_review_overrides.json` e reaplicados tanto no caminho
per-report como no bulk sync.

## Remediação pós-merge e audit trail

A validação pós-merge da PR #135 encontrou dois problemas LEVEL 1 no workflow e
um problema na persistência da semântica de review. Foram corrigidos sem mudar
o contrato de licenciamento ou qualquer lógica analítica:

1. A run `34528518797` mostrou que a aquisição de imagens terminava mas o passo
   de publicação falhava ao tentar `git add` do checkpoint transitório
   `data/rapidapi_usage_inflight.json`, que é removido deliberadamente no fim de
   uma execução bem-sucedida.
2. PR #136 (`bfb4ca22b4777b276ca59a20e5a2c34810cd64c0`) tentou tolerar a ausência
   desse path. **SUPERSEDED:** a validação mostrou que essa abordagem podia
   produzir um workflow verde sem garantir staging dos outputs persistentes.
3. PR #137 (`3255c206d1a3af313dc923d345f7fe6184a69305`) tornou explícito o contrato
   correto: o publish de sucesso stageia apenas registry, review queue, usage
   log e assets persistentes. A run real `34529527680` concluiu com sucesso e
   publicou o commit `668bba1464bab335a67daf8405fcae927244577d`.
4. Essa execução real revelou que a fila derivada sobrescrevia o reason curado
   de Blockx com a mensagem genérica de ausência de P18. PR #138
   (`017661f756e53160d417a8a3e28dd980c6aa0061`) separou a decisão curada numa
   fonte declarativa e adicionou testes para os dois caminhos de escrita.
5. A run end-to-end `34530676514` passou tanto `Obter rankings e fotografias
   licenciadas` como `Publicar acervo` e publicou
   `f25c04949505560205eea5fe7ef66c71a75e7a6b`. Nesse estado, Blockx permanece
   `AB` e `data/player_images_review.json` preserva
   `LICENSED_SOURCE_UNAVAILABLE`.
6. CI pós-merge da PR #138 (`34530676570`) e GitHub Pages (`34530675469`)
   terminaram com sucesso.
