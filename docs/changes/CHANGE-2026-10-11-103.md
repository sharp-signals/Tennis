# CHANGE-2026-10-11-103 — Codex developer fast path

Estado: **IMPLEMENTED IN BRANCH / TESTING**  
Issue: #232  
Level: **1 — LOW RISK**

## Objetivo

Reduzir a latência do ciclo BRAIN → Codex sem alterar comportamento do
Fenzobot nem remover gates de validação.

A mudança atua apenas no processo de desenvolvimento:

- contexto delta-first;
- testes dirigidos durante o loop;
- full CI apenas no checkpoint final quando o risco a exige;
- política explícita para main drift;
- outputs intermédios mais curtos.

## Problema observado

Em alterações recentes, grande parte do tempo não foi gasta a escrever código,
mas a:

1. reler contexto já conhecido;
2. correr a full suite após pequenas correções;
3. repetir review quando `main` avançava apenas em dados independentes;
4. sincronizar branches antes de saber se existia overlap material;
5. repetir relatórios extensos em cada iteração.

## Implementação

### `AGENTS.md`

Passa a exigir:

- início pelo diff/brief ativo;
- expansão de contexto apenas quando o delta toca nova fronteira;
- validation ladder em duas fases;
- política de main drift;
- full CI final obrigatória para Level 2/3 e hotspots;
- outputs intermédios curtos.

### `scripts/plan_validation.py`

Ferramenta read-only que:

- recebe o nível da mudança;
- inspeciona paths alterados via Git ou argumentos explícitos;
- identifica hotspots/domínios críticos;
- recomenda targeted tests;
- decide se full CI é obrigatória no checkpoint final;
- classifica drift de `main` em:
  - `SYNC_NOW`;
  - `FINAL_SYNC_ONLY`;
  - `REVIEW_ONCE_THEN_FINAL_SYNC`;
  - `NO_SYNC_NEEDED`.

A ferramenta não edita código, branches, CI ou dados.

### Guia operacional

`docs/development/CODEX_FAST_PATH.md` documenta o workflow recomendado e
exemplos de utilização.

## Preservado

Não altera:

- motor Fenzobot;
- pesos/fatores;
- thresholds;
- pricing/edge;
- PAPER/GREEN/REAL;
- snapshots;
- settlement;
- workflows produtivos;
- branch protection;
- gates finais de Level 2/3.

O fast path elimina repetição no loop; não reduz o nível de validação final
exigido por mudanças materiais.

## Critério de sucesso

Depois do merge, o Codex deve conseguir determinar rapidamente:

1. que contexto precisa realmente de ler;
2. quais testes correr durante a edição;
3. quando esperar pela full CI;
4. se um avanço de `main` exige sincronização imediata.

A melhoria deve ser avaliada nas próximas mudanças pela redução de ciclos de
full CI/re-sync/re-review, não por reduzir testes obrigatórios.
